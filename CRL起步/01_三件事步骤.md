# 三件事：单任务 → 短任务序列 → 实测成本

日期：2026-11-02。阶段安排依据当前条件制定，不是承诺完成论文的日期。

## 第一件事：跑通单任务，建立最小工作闭环

**设备与阶段：公司 CPU，现在可以开始。** 预计先安排 1—2 小时主动学习；机器运行时间以实测为准。

### 步骤

1. 按 `00_从这里开始.md` 用 `single_task.py` 训练 Pendulum，先短跑检查，再做 10000 步。
2. 看 `summary.json` 和学习曲线，区分随机策略、未训练策略、训练后策略。
3. 重载 `model.zip`，生成 GIF，观察是否学会摆起及稳定。
4. 阅读 `single_task.py` 的 `train()`、`evaluate()` 和 `Progress`，再看 SB3 中 `SAC.train()`。
5. 写下五项自测答案。

### 完成条件

- 环境可以 reset/step；有限奖励、正确结束每局。
- 实际执行了梯度更新，参数发生有限变化。
- 独立评估可运行，模型保存重载动作一致。
- 能解释回报及学习趋势。单次短训练无提升并不代表环境故障；若 10k 无提升，先记录再做有依据的排查。

### 从入门过渡到机器人单任务

回学校后另建 Meta-World 环境，固定原仓库使用的 Meta-World commit，先验证随机动作能运行，再训练原仓库 `simple` 单任务。原任务 0 是 `hammer-v2`。

**以下是待验证入口，不是公司电脑上已经跑通的命令。** 用对应 Meta-World 环境的 Python，在原仓库目录直接运行 `run_sac.py`，避开启动器写死的 `python3`：

```powershell
Set-Location '.\CRL起步\CKA-RL\experiments\meta-world'
# 此处 python 必须是另外安装好的 Meta-World 环境解释器。
python run_sac.py --model-type simple --task-id 0 --total-timesteps 10000 --buffer-size 20000 --eval-every 5000 --num-evals 3 --tag school_single_smoke --save-dir agents/school_single_smoke
```

10000 步只验证运行和更新，不要求机械臂学会 hammer。正式单任务应根据曲线增加训练步数。不要把入门成功标准硬套到较难的机器人任务。

## 第二件事：跑通两三个任务，弄清知识如何保留和复用

**阶段：单任务可靠后，优先在学校电脑推进。今天不必做完。**

### 步骤

1. 先读论文问题设定和原代码任务列表，确定任务边界、评估是否使用任务标识、旧任务是否能重新交互。
2. 先在同一框架运行单任务独立训练与顺序微调，建立基本对手。
3. 再运行 CKA-RL 的前 2—3 个任务，保持相同环境、交互预算和种子。初期使用短运行检查，研究比较时给予足够训练。
4. 每次任务训练结束后评估所有已学任务，保存矩阵：行是学到第几个任务，列是在哪个任务评估。不要只看当前任务回报。
5. 记录首任务策略、共享部分、知识向量、组合系数、旧任务模型文件分别如何生成和读取。
6. 如需观察合并，要让向量数量超过知识池容量，并记录触发时刻。两个任务并不一定已达到合并条件。

### 完成条件

- 能分别指出新任务如何复用旧知识、旧任务如何选择对应策略。
- 能区分“保留旧任务的独立模型”和“一个共享系统本身没有遗忘”。
- 评估矩阵中的历史任务列都真实执行过，不把未测值写成 0。
- 统一记录知识池、各任务模型、共享参数和其他持久状态的资源成本。知识池容量有限不等于系统总存储不增长。

### 当前研究候选

基于 CKA-RL 考察合并依据：参数余弦相似度是否足以选择知识向量合并对象？使用策略行为变化作为候选依据是否有收益？

先复现和查近邻工作，再决定方法。若需要探测状态，明确它来自当前任务还是历史记忆，并计入资源；只读评估环境的结果不能被偷偷拿来选合并对象。

不先把“余弦换 KL”“加一个权重”写成已确定创新；必须说明已有方法未解决的具体问题，并取得可重复证据。

## 第三件事：实测成本，决定实验规模和是否租卡

**从第一件事就开始记录；正式预算依据 Meta-World 实测。**

### 步骤

1. 先记录 CPU 入门运行的 `steps_per_second_including_periodic_eval`、RSS 和模型字节，学会看资源账。
2. 学校 GPU 上跑代表性的机器人任务；把预热、稳定训练、定期评估分开计时。记录设备型号、CPU、显存峰值、进程内存、环境步数、梯度更新数。
3. 再做短序列实测，观察随着已学任务增多，评估时间和模型存储是否增长。
4. 估算一次完整比较：`方法数 × 随机种子数 × 任务数 × 每任务训练与评估耗时`，额外计入独立任务基线、消融和失败重跑。
5. 先在本机调通并确定配置，只有当连续运行确实成为瓶颈时，才考虑租卡。租前明确每小时价格、预计小时数、存储费和可接受的月度上限。

### 一个只用于理解的算例

若实测一条任务序列需要 8 小时，3 个方法 × 3 颗种子就是 72 小时，尚未包括独立任务基线和消融。再乘实际租价得到预算。这里的 8 小时是示例，不是对你机器的预测。

### 完成条件

- 能给出本机和租用机器上的实测成本，不能从 Pendulum 吞吐直接外推 Meta-World。
- 显存不足、CPU 仿真慢、评估耗时长分别定位，避免误以为换更贵 GPU 都能解决。
- 保留一份覆盖方法、种子、任务序列、时间和费用的预算表。当前不创建租赁、不产生付费操作。
